# AGC「代理提醒」开放能力 · 申请材料

> 路径：AGC → 项目设置 → 开放能力管理 → 代理提醒 → 新建业务申请（服务开通申请）
> 审批时间以页面显示为准（本次实测显示 **3 个工作日**）。
> 用途：申请通过前，代理提醒可用数为 0，番茄钟到点提醒与任务/目标截止提醒会**静默失效**。

---

## 一、申请原因（使用场景 + 必要性）——可直接复制

```
本应用为效率工具类：个人目标拆解与任务管理。用户可主动开启「番茄钟专注计时」（默认 25 分钟），
并可为任务/目标设置截止日期及提前提醒（默认提前 1 天 / 3 天）。这两处都必须在用户自己设定的
时间点准时提醒，否则功能不成立：

1）计时提醒：用户开始专注后常会退到后台或锁屏，此时应用进程被系统冻结，前台计时器停止运行。
   若不使用代理提醒，计时结束时用户无法收到任何提示，不知道本轮专注已结束，专注计时功能等于失效。

2）临期提醒：任务与目标的截止时间通常在未来数天，届时应用未必处于运行状态。
   提前提醒用户才能在截止前留出处理时间，这是本应用的核心价值之一。

两种提醒均由用户主动设定的时间触发，不含任何营销或运营推送，也不做周期性打扰：
每次专注结束仅 1 条，每个任务/目标在其截止前仅 1 条。
```

> 512 字符上限，上面约 340 字符，直接粘贴即可。

## 二、通知标题 / 文本（与包内实际文案一致，审核可能核对）

| 场景 | 通知标题 | 通知文本 |
|---|---|---|
| 专注结束 | `专注完成` | `任务『跑步训练』已完成一轮专注，休息一下吧` |
| 休息结束 | `休息结束` | `可以开始下一轮专注了` |
| 任务截止 | `任务截止提醒` | `背单词 即将到期` |
| 目标截止 | `目标截止提醒` | `目标『3 个月跑完半马』即将到期` |

（`『』` 内为用户的真实任务/目标名，运行时替换）

## 三、通知场景

若表单为选择项，选 **计时提醒** 与 **临期提醒**（官方列举的允许场景，与本应用逐条对应）。
若需文字补充：

```
番茄钟专注计时结束提醒（计时提醒）；任务与目标的截止日期提前提醒（临期提醒）。
```

## 四、通知频率

```
低频、且全部由用户主动触发，无定时群发、无营销推送。
· 番茄钟：每完成一轮专注 1 条，条数取决于用户当天自己发起几次（典型 2–8 条/天）；
· 截止提醒：每个任务/目标在其截止前仅 1 条（提前 1 天 / 3 天），且同一条目重排时先取消旧提醒。
```

## 五、上传附件（回答"是不是要传 App 界面"）

2. **任务详情页的截止日期 + 提前提醒设置入口**
3. **沿用现有的「专注完成」通知形态**（可选：通知栏截图）

传图注意：

- 文件名建议用英文/拼音，避免中文名在某些上传控件里乱码

## 六、通过之后（容易漏的一步）

权益通过后，**必须重新生成 Profile 并改成手动签名**，否则新申请的开放能力不会生效。
建议与 P0 第 3 项「release 签名 + 混淆」合并排期，一次做完。

## 七、验证方式

### 7.0 前置条件（不满足这一条，下面全部白做）

**必须打「release + 手动签名（用含代理提醒能力的 Profile）」的包。**

代理提醒能力是**写在 Profile 里授权**的（`app-services-capabilities`）。
DevEco 的「自动生成签名」产出的是**调试 Profile**，里面没有这个能力 →
不管代码多正确，`publishReminder` 一定返回 **1700002**。

> 一句话自查：`.p7b` 里 `app-services-capabilities` 有没有代理提醒那一项。
> 没有 → 这个包验不了，先回去更新 Profile。

### 7.1 要分清两件事（这是关键，能省掉一次瞎等）

| 想确认的 | 什么时候能知道 | 要不要等 / 改时钟 |
|---|---|---|
| **① 权益有没有生效**（能力被不被系统接受） | **注册那一刻**就出结果，**秒级** | ❌ **不用等、不用改** |
| **② 到点会不会真的弹出来** | 得等到那个时刻 | ⚠️ 番茄钟 15 分钟；临期提醒见 7.4 |

很多人卡在②上干等，其实①才是"权益验证"，而它**秒级就能出结论**。

### 7.2 第一件事：秒级验"权益已生效"（推荐先做这个）

#### 7.2.0 ⭐ 最省事：用「设置 → 测试提醒」（已内置，不用抓日志）

应用里已经做好了一个自检入口：**设置页 → 通知分组 → 测试提醒 → 点「发送」**。

它的做法是**真的去发布一条 60 秒后的代理提醒**，然后把这个调用的结果直接弹在界面上：

| 弹窗 | 含义 | 下一步 |
|---|---|---|
| **提醒功能正常** | 系统已接收 → **权益生效** ✅ | 按提示切到桌面/锁屏，等 60 秒确认能收到 |
| **提醒功能未生效**（附错误码） | 通常是 **1700002** → 受管控 ❌ | 回到 7.0 检查 Profile / 签名 |

这一步**不需要连电脑、不需要抓日志**，是最快的"到底行不行"。

> 为什么专门做这个入口：代理提醒受管控时，`publishReminder` 的失败**只落在日志里、
> 用户侧完全无感**（表现为"离开应用后不提醒"）。这个入口把同一调用的结果搬到界面上。
> 平时它也是个正经功能——用户可随时自测"我的通知是不是被系统关掉了"。

#### 7.2.1 或：抓日志看（信息更全，可看到对账数字）

抓日志（DevEco 的 Log 窗口过滤 tag，或命令行）：

```bash
hdc shell hilog | grep -E "PomodoroService|DeadlineReminderService"
```

**判据 A —— 开始专注时立刻看：**

- `registerBackgroundReminder: id=xxx, triggerAt=...` → **系统收下了，权益已生效** ✅
- `registerBackgroundReminder failed: ... 1700002 ...` → **仍被管控**（权益没绑上 / 签名没换 / 打的是调试包）❌

**判据 B —— 启动后约 3 秒自动打的一条对账日志（更权威）：**

```
DeadlineReminderService verifyReminders: local(task=N, goal=M), systemValid=K
```

| 情况 | 含义 |
|---|---|
| `systemValid ≥ local`（且 local > 0） | 本地排期的，系统侧确实都在 → **权益生效** ✅ |
| `local > 0` 而 `systemValid = 0`，并伴随 `系统侧没有任何有效代理提醒…代理提醒很可能受管控` | **权益未生效**——这是唯一可观测的地方（失败只落日志、用户侧完全无感）❌ |
| 两者都为 0 | 说明还没有任何任务/目标设了未来截止日期，**换一个已排期的任务再看** |

> 这条日志是**受影响场景下唯一的诊断手段**，务必留着。

### 7.3 第二件事：番茄钟真实弹窗 —— 15 分钟就能验，**不用改系统时间**

番茄钟的触发时刻是**相对当前时间**算的：

```
triggerTime = 现在 + 剩余时长 + 5000ms（BG_REMINDER_LEAD_MILLIS，避免与前台完成通知双弹）
```

它与"系统时钟是不是准"无关，所以**最短时长就是最快验证法**：

1. 进番茄钟沉浸屏，选 **15 分钟**
2. 开始专注 → **按 Home 退到后台**（或锁屏。要真验"进程被冻结也能弹"，可以**直接强杀应用**）
3. 抓日志确认已注册（见 7.2 的判据 A）
4. 等 15 分钟 → 应弹出「**专注完成**」
5. 点这条提醒 → 应**直达该任务详情页，并恢复全屏番茄钟**

### 7.4 临期提醒：**最快只能等到今晚 23:59**（这不是 bug，是设计）

代码事实（`TaskDetailPage` / `GoalDetailPage`）：

```ts
// 取当天 23:59:59 作为截止时间
this.editDeadline = new Date(value.year, value.month, value.day, 23, 59, 59).getTime()
```

而触发时刻 = `截止时间 − 提前量`，提前量只允许 **0 / 1 / 3 / 7 天**。于是：

| 截止日期 | 提前量 | 触发时刻 | 结果 |
|---|---|---|---|
| **今天** | **0** | **今天 23:59:59** | ✅ **最早的可测触发点** |
| 明天 | 1 | 今天 23:59:59 | ✅ 同样落在今晚 |
| 今天 | 1 | 昨天 23:59 | ⚠️ 已过 → 走的是**"立即触发"兜底分支**（`notificationManager.publish` 本地即时通知），**不经过代理提醒，验不了权益** |
| 后天 | 3 | 今天 23:59:59 | ✅ |

**注意第三行这个坑**：它确实会弹一条通知，但那是**应用自己发的本地通知**（不需要权益也能发），
**别用它来判断代理提醒是否生效**。要验代理提醒，必须让 `advanceDelivery > now`。

所以最省事的做法：**把某个任务的截止设成"今天"、提前量设 0，今晚 23:59 顺势看一眼。**

### 7.5 关于"直接改手机时间"—— 可以但不建议

代理提醒存的是**绝对年月日时分秒**，把系统时间往前调，理论上会让它提前触发。但有四个代价：

1. **会被自动同步回去**：手机若开着「自动设置日期与时间」，你改完系统会自己校正回来，
   反而错过触发点 → 要改就**必须先关掉自动**
2. **连带影响面很大**：云同步的 token 有效期判断、HTTPS 证书校验（时间错位会直接报错）、
   日志时序、以及**"今日专注/今日投入"的统计口径**（`HomeViewModel` 按当前时间算当天起始）全都会乱
3. **必须改回来**，否则数据时间戳全错
4. **调回来可能再弹一次**：触发点已弹过的提醒不会消失，而调回正确时间后
   其他已注册提醒会重新变成"未来"，可能重复弹出

**结论：临期提醒不必为它专门改时钟。** 它和番茄钟**共用同一个 `publishReminder` 链路**——
番茄钟一旦验通（7.2 + 7.3），说明**权益和链路都没问题**，临期提醒只剩"提前量算法"这一个
纯计算问题，等今晚 23:59 顺势看即可。

### 7.6 推荐顺序（今天就能走完）

1. 打 **release + 手动签名**包（前置条件，见 7.0）
2. **设置 → 测试提醒 → 发送** → 弹「提醒功能正常」= 权益已生效（7.2.0，秒级）
3. **切到桌面或锁屏 → 等 60 秒** → 应收到测试通知
   —— 这条同时完成了"权益生效"与"进程不在前台也能弹"的端到端确认
4. （可选，验真实业务路径）选 15 分钟 → 开始专注 → 退后台 → 等 15 分钟 →
   看是否弹、点击是否直达任务详情（7.3）
5. 今晚 23:59（截止设"今天"、提前量 0）→ 顺势看一眼临期提醒（7.4）

## 八、这个能力到底是什么（心智模型，避免误用）

### 一句话
代理提醒**不是推送通道，而是"把闹钟托管给系统"**：应用在运行时登记"某时刻要提醒什么"，
到点由**系统**代为弹出 —— **即使应用进程已被冻结或杀掉**。

它解决的正是一个死结：**应用不运行时，自己发不出通知**（进程被冻结），
而"到点必须提醒"的场景恰恰就发生在应用不运行的时候。

### 三种"通知"的区别（别混）

| 机制 | 谁发出 | 应用没运行能收到吗 | 用途 |
|---|---|---|---|
| **本地通知**（`notificationManager.publish`） | 应用自己 | ❌ **不能**（进程冻结就发不出） | 应用正在运行时的即时提示 |
| **代理提醒**（`reminderAgent`，本能力） | **系统代发** | ✅ **能** | **定时提醒**（用户设定的时间点） |
| **Push Kit**（推送服务） | 服务端 → 系统 | ✅ 能 | 服务端主动触发的消息 |

### 所以"能不能用它给用户推送通知"？—— 分情况

| 想做的事 | 可行性 |
|---|---|
| 到点提醒（番茄钟结束 / 任务临期），**应用没运行也要弹** | ✅ **正是代理提醒的用途** |
| 应用**正在运行时**立刻弹一条 | ✅ 可行，但应该用**本地通知**，不是代理提醒 |
| 服务端主动发消息（活动 / 公告 / 实时事件） | ⚠️ 需要 **Push Kit**（另一套权益，且要服务端 + push token） |
| 用代理提醒发**营销 / 运营**内容 | ❌ **明确禁止** —— 超出约定场景会**立即禁用权益** |

### 一个必须知道的技术约束
**提醒内容是"发布时"就固定下来的**，到点由系统渲染 → **不可能在到点那一刻动态生成内容**。
本应用的用法没问题：发布提醒时应用正在运行，能读到任务名 / 目标名并写进文案
（例如「任务『背单词』即将到期」），这正是可行动的前提。

### 用户控制权（审核也会看）
用户可以在**系统设置**中关闭本应用的通知 / 提醒 → 应用必须能探测到并优雅降级，
而不是当作"发成功"自欺欺人。项目已有 `DeadlineReminderService.verifyReminders`
做这类校验（见第七节第 4 条），这也是"静默失效"能被及时发现的原因。
