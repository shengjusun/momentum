# 平板横屏适配：问题分析与可行性方案

> 状态：方案待评审（未动代码）
> 前置事故：2026-09-11 把 `breakpointState.isTablet` 从「恒 false」修成「平板 true」，
> 结果一次性激活全应用 6 个页面的平板分支，界面大面积变形，已回滚。

---

## 一、问题的本质：三件事被绑在了一个开关上

现在「平板适配」这件事实际包含三个互相独立的决策，但它们都挂在同一个布尔量
`breakpointState.isTablet` 上：

| 层 | 决策内容 | 现在由谁决定 |
|---|---|---|
| 识别层 | 这台设备/这个窗口算不算「宽」 | `breakpointState.isTablet` |
| 布局层 | 这一页用单栏还是双栏 | 各页 `if (breakpointState.isTablet)` |
| 尺度层 | 内容限宽 640 还是铺满 1080 | 各页 `getContentConstraint()` |

**后果**：开关一翻，6 个页面 × 8 处分支同时改变。任何一处没调好，都是「全应用一起出问题」，
而且分不清是谁的锅。这就是上次事故的机制。

## 二、为什么「直接拉伸」没有横屏优势

这是第二个独立问题，和上面的耦合无关。

当前手机布局是「单栏 + 居中限宽 640」。如果只是把 `maxWidth` 从 640 改成 1080：

- 一行文字、一张卡片被拉到 1080 宽 → **每行字数变多，阅读反而变累**
- 信息结构没变，只是等比例放大 → 视觉上就是「竖屏拉宽」
- 内容实际利用率仍然很低，空白只是从「两侧」挪到了「卡片内部」

**横屏的真正优势不是「同一列变宽」，而是「能并排放第二列信息」**：

- 主内容 + 附属内容同屏（列表 ↔ 详情、对话 ↔ 产出、信息 ↔ 操作）
- 减少层级跳转：手机上要点进去、返回的操作，平板上同屏完成
- 信息密度提升：多列网格、更少的滚动

所以正确的路径是 **先做分栏（结构性收益），再谈铺满（尺度性收益）**，而不是反过来。

## 三、还有一个被忽略的坑：断点粒度太粗

现有断点：`sm < 600 vp ≤ md < 840 vp ≤ lg`，`isTablet = (bp === 'lg')`。

按这台平板（2800×1840 @ density 2.5）：**竖屏 736vp → md，横屏 1120vp → lg**。

由此暴露两个问题：

**问题 A：平板竖屏享受不到任何适配。** 736vp 落在 md，`isTablet=false`，
平板竖屏完全走手机单栏布局 —— 用户感知就是「平板竖屏和手机一样」。

**问题 B：手机横屏会被误伤。** 手机横屏（如 2400×1080 @3 = 800×360vp）宽度到 800vp，
落在 md；若将来放宽到 lg 判断，手机横屏就会进双栏，而它**高度只有 360vp**，双栏会挤成一团。

**结论：不能用「宽度」这一个维度判断形态，要用「宽度 + 高度」双条件。**
行业通行做法（window size class）是同时看宽高：真正的平板/折叠屏展开态，
是**最短边 ≥ 600vp**；手机横屏最短边只有 360vp，天然被排除。

---

## 四、改进思路：三层解耦 + 按页灰度

核心两句话：
1. **把「识别 / 布局 / 尺度」拆开**，各自有独立的信号和开关，不再共用一个 `isTablet`。
2. **按页灰度**：一次只让一个页面进入宽屏模式，改一页、验一页、提交一页；
   每页有独立开关，出问题只回退这一页。

### 目标结构

```
① 识别层：WindowFormState（新）
   输入：窗口 宽 × 高（vp）
   输出：form = compact / medium / expanded
        （expanded 要求 最短边 ≥ 600vp，手机横屏不会命中）

② 布局层：每页读 form，但每页有独立开关
   if (form >= medium && WideFeature.routeEnabled)  → 双列网格
   if (form === expanded && WideFeature.taskDetail) → 双栏
   （开关默认全关，验一页开一页）

③ 尺度层：内容宽度三档常量，由 form 选择
   compact → 640 / medium → 840 / expanded → 1080
```

### 关键技术约束（已踩过的坑）

**`@Local windowWidthVp` 驱动 `constraintSize(getPageConstraint())` 实测不重渲染**
（日志已打印 `vp=1120`，布局仍停在 640）。原因是 `constraintSize(方法返回值)`
里的方法调用不参与依赖追踪。

→ 因此**宽窄信号只用于 `if/else` 切换布局分支**（可被追踪），
不要用于计算 `constraintSize` 的数值。限宽也写成三档常量，用 if/else 选。

```ts
// 反例（不重渲染）
.constraintSize(this.getPageConstraint())

// 正例（if/else 分支可追踪）
if (this.form === 'expanded') {
  Column() { ... }.constraintSize({ maxWidth: 1080 })
} else if (this.form === 'medium') {
  Column() { ... }.constraintSize({ maxWidth: 840 })
} else {
  Column() { ... }.constraintSize({ maxWidth: 640 })
}
```

## 五、分期路线（按风险从低到高）

每期独立可交付、可真机验证、可单独回退。

### Phase 0 — 基建（不改任何视觉）
- 新增 `WindowFormState`（`@ObservedV2`）：用 `window.getLastWindow()` +
  `windowSizeChange` 计算「宽 × 高」，产出 `compact / medium / expanded`
- 与现有 `breakpointState` **并存**，不动它，避免影响存量 `isTablet` 分支
- 加一个全局 `WIDE_FEATURE` 开关表（各页默认 false）
- 验收：真机日志打印 form 值；手机竖屏=compact、平板竖屏=medium、平板横屏=expanded、**手机横屏=compact**

### Phase 1 — 纯尺度（视觉风险最低，先见效）
- RoutePage：双列网格阈值由 `bp !== 'sm'` 改为 `form >= medium`（现有逻辑本就最接近，只换判断源）
- HomePage：四象限矩阵 + 标题区宽度按 form 三档铺满（结构不变，只调尺度和 padding）
- 验收：横屏不再有两侧大片留白，且文字行宽不超过阅读上限

### Phase 2 — 静态双栏（纯展示，交互简单）
- TaskDetailPage：左信息+番茄钟 / 右步骤+操作
- GoalDetailPage：左目标卡 / 右任务列表
- 这两页是「并列展示」，无跨栏联动，最容易做对
- 验收：横屏两栏比例合理；竖屏/md 回落单栏；旋转、分屏不串

### Phase 3 — AI 页双栏
- 对话 + 右侧方案栏；侧栏有展开/编辑/删除/确认等交互，且依赖 `latestPlanMessage`
- 需额外验证：流式输出中侧栏更新、空态（无方案时不显示侧栏）

### Phase 4 — 首页双栏（最难，放最后）
- 点击象限切右栏、拖动换格与右栏联动、半模态在宽屏下是否保留
- 依赖 Phase 0 解决 `@Local` 不重渲染问题
- 需要单独设计：宽屏下「点击象限」和「拖拽换格」的交互是否仍然成立

### 并行决策项 — 底部导航在宽屏怎么办
现在 `isTablet` 时是「480vp 靠左」，这正是用户上次说的「挤在左边」，观感不佳。
两个方向，建议单独定：
- **A 保持现状居中**：宽屏时也居中（改动最小，但没利用横屏）
- **B 改侧边导航**：横屏用左侧竖排导航栏（真正利用横屏、符合平板习惯，但工作量最大，涉及 MainTab 整体重构）

## 六、每页验收清单（真机，缺一不可）

| 场景 | 检查点 |
|---|---|
| 冷启动首帧 | 布局正确，无闪烁/跳变 |
| 横竖屏旋转 | 断点跟随切换，无双栏残留 |
| 分屏 / 自由多窗 | 拖到任意宽度都落在正确档位（含跨档临界） |
| 从窄拖到宽 | 单栏 → 双栏切换不崩、不丢状态 |
| 三态 | 加载 / 空 / 错误 三态也符合宽窄布局 |
| 底部避让 | 内容不被导航栏遮挡 |
| 手机横屏 | 保持单栏（不被误判为平板） |

## 七、可行性结论

- **技术上可行**：8 处分支代码都已写好，缺的是「正确的判断源」和「逐页验证」，
  不是从零开发。工作量主要在验证，不在编码。
- **风险可控**：三层解耦 + 按页开关后，单次改动影响面从「6 页」收敛到「1 页」。
- **收益明确**：Phase 1 就能消除「拉伸感」；Phase 2/3 才开始拿到横屏的真正价值（同屏双栏）。
- **最大不确定性**：`@Local`/响应式在 `constraintSize` 场景不重渲染的问题，
  需要 Phase 0 用 `if/else` 分支方案绕开并真机确认。
- **建议节奏**：Phase 0+1 一起做（低风险、快见效），验收通过后再逐页推进 Phase 2/3/4。

## 八、需要你拍板的三件事

1. **先做哪条线**：是「Phase 0+1 打底、稳扎稳打」，还是先挑一页做完整双栏看效果（比如 RoutePage/任务详情）？
2. **底部导航**：保持宽屏居中，还是做左侧竖排侧边导航（A / B）？
3. **平板竖屏（md）要不要适配**：现在它完全走手机布局。要不要在 md 给轻量适配（如多列网格、放宽限宽）？
