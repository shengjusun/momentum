### P1-1 冷启动固定多等 600ms+ ✅ 属实

| 证据 | 位置 |
|---|---|
| `COLD_START_INIT_DELAY_MS = 100` | `CommonConstants.ets:17` |
| `COLD_START_ROUTE_DELAY_MS = 500` | `CommonConstants.ets:20` |
| 100ms 后才启动 init | `MainTab.ets:92` |
| 三个 VM **串行 await**（settingsVM → homeVM → routeVM） | `MainTab.ets:114 / 126 / 134` |
| 再等 500ms 才恢复路由 + 消费深链 | `MainTab.ets:155 / 170` |

**点通知进详情页确实被拖慢**：`consumePendingDeepLink()` 在 500ms 回调里执行。

**修法与优先级判断（比"并行省 40-60%"更准确）**：
- 三个 init 各自独立 try-catch、互不依赖数据，`Promise.all` 可行 ✅。但真正的**大头是两个固定 setTimeout（600ms 纯等待）**，与并行无关
- 500ms 那个的语义是"等 Navigation 挂载"——不能直接删，正确做法是**改成 Navigation 就绪回调驱动**（或实测后压到 50-100ms）
- 100ms 那个可以直接压到 0（aboutToAppear 里 Navigation 尚未挂载的问题，用首帧回调替代）
- ⚠️ **我复核时发现审查没提的一点**：`settingsVM.init` 里的冷启动 merge 跑在 `registerSnapshotProviders` **之前**（`MainTab:114` vs `:141`），此时快照 provider 为 null，`buildLocalSyncDataBundle` 传空串（`SettingsViewModel:386-387` 有 null 保护，merge 方向安全）——这正是它"必败空转"的第二个原因

### P1-2 勾选任务 = 全量 stringify + 巨型指纹 ✅ 属实（实际是 5 次，不是 3 次）

完整链路（每步都有出处）：

```
toggleTask (HomeViewModel:587)
 → 200ms 防抖 → persistData（StorageManager:226 全量 stringify ①）
 → emit SYNC_NEEDED → buildLocalSyncDataBundle
     goalsJson/todosJson 走 provider（② ③）
     settingsJson/profileJson 直接 stringify（④ ⑤）   SettingsViewModel:386-408
 → scheduleSync 2s 防抖 → smartSync → shouldUpload
 → buildFingerprint：四段 JSON **全文拼接**成一个巨型字符串
    + 对 profileJson 全文跑正则替换                    CloudSyncService:69-76
 → upload：全量 upsert 整条 UserSyncData
```

- 指纹**不是哈希，是全文拼接** → 内存峰值 ≈ 数据量 2-3 倍，每次脏检查都做一遍
- "3000 条 60-120ms"无法静态确证，但结构上方向正确
- **注意这不是乱写，换来了正确性**：全文比对是最可靠的脏检查。性价比最高的修法是**指纹改哈希**（对拼接结果算一次 hash，比较哈希值）——改动极小，同时消掉巨型字符串和正则开销
- "1MB 上传"是 CloudDB **单条记录全量同步**的架构决定，改增量是大工程，**不建议现在动**（与上架无关）

### P1-3 冷启动提醒重建写盘风暴 ✅ 属实（我上一轮漏掉的）

- `rescheduleAll` → `cancelAllTaskReminders` → 每个 `cancelAgentReminder` **逐个 `persistReminderIds()`** → 然后 `scheduleTaskDeadlineReminder` 成功后再逐个 `persistReminderIds()`
- 50 任务 + 20 目标 ≈ **140 次全量 Map 序列化 + saveData**（O(n²) 序列化）
- 减轻情节：`saveData` 是异步且走 `StorageManager` 写锁串行化，**不阻塞首帧渲染**，但会排队挤占冷启动 IO/CPU
- 修法极简：**批量前后各持久化一次**（cancelAll 后一次、全部 schedule 完成后一次）
- 说明：这是我上一轮改 `verifyReminders` 时**应该顺手发现而没发现的**，是我的疏漏
