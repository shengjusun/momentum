# 第三方全面分析报告 · 复核意见

> 复核人：阿墨　日期：2026-09-16
> 被复核对象：`comprehensive-analysis-report.md` + `analysis-backend.md` / `analysis-quality.md` / `analysis-release.md`
> 复核方法：**逐条对代码/官方依据实测**，不采信报告自身引用的 README 清单

## 一、总体评价

报告覆盖面广、结构专业、问题分档清晰，**10 项严重中有 4 项站得住**，对质量与性能部分的细节敏感度不错。

但存在 **7 处结论性误判**，其中 **1 条建议若执行会直接破坏云服务**，另有 2 处是本项目**已经明确更正过、又被重新提出**的错误结论。

**根因**：报告把 `README.md` 的过期待办清单当作事实依据，未与代码和官方依据交叉验证。而 README 本身有 3 处过期（详见第四节）。

## 二、必须纠正的误判

### ❌ 错误 1（危险）｜S10 / S3：建议删除 `rawfile/agconnect-services.json`

报告称它是"副本"，建议"不必要则删除"。

**实测**：该文件是 **AGC 云服务的必需配置**（登录 / CloudDB / 云存储全靠它），项目明确列为**勿动清单**。删除后云同步、华为账号登录、AI 拆解**全部失效**。

**判定：绝不能执行。** 若存在两份，正确做法是保证同步，而不是删除 rawfile 那份。

### ❌ 错误 2（重犯）｜S9 / S2：`DETECT_GESTURE` 是受限权限、P0 阻塞

报告称其为 `system_basic` 级受限权限，可能被拒审。

**实测**：项目 `docs/上架素材/智感握姿说明.md` **专门更正过这个误判**，援引官方权限表原文：

```
ohos.permission.DETECT_GESTURE
权限级别：normal
授权方式：系统授权（system_grant）
```

`normal / system_grant` = **安装即授予、不弹窗、不需 AGC 申请**，真机功能可用已验证。报告引用的 README:55 正是那条**已被作废**的旧结论。

**判定：从 P0 阻塞项中删除。** 唯一可做的可选优化是"补一个用户开关"，且属性是产品体验建议、非审核硬要求。

### ❌ 错误 3｜R-M2：浅色主题"极不完整 / 浅色模式不可用"

报告假设 `base` 是深色，推断浅色模式会回退成深色背景。

**实测**：

| 目录 | 项数 | 说明 |
|---|---|---|
| `base/element/color.json` | **122** | `bg_page=#F5F6FA`、`bg_card=#FFFFFF`、`text_primary=#1C1C1E` → **base 就是浅色** |
| `dark/element/color.json` | 122 | 深色覆盖层，完整 |
| `light/element/color.json` | 1 | `start_window_background` —— **只放差异项是正确做法** |

**判定：主题体系健康，从 P1 中删除。** 注意 `dark` 也是 122 项（报告说 145 行是行数，非项数）。

### ⚠️ 错误 4｜S2：RoutePage 强制登录与游客模式矛盾

**定位错误**：报告引的 `RoutePage.ets:848-852` 实际是 `await routeVM.init()` + 数据源同步；`RoutePage` **全工程无任何登录判断**（已全文检索 `ROUTE_NAME.LOGIN`）。

**但报告的问题类别是对的，真凶在别的文件**：

```
GoalDetailPage.ets:1384-1387
if (!settingsVM.userProfile.isLoggedIn) {
  globalNavStack.replacePath(new NavPathInfo(ROUTE_NAME.LOGIN, null))
}
```

游客能进路线页、能手动创建目标，但**一点开目标卡片就被强制踢到登录页** → 与 `MainTab` 注释承诺的"游客可用路线功能"矛盾。这才是需要决策的那一处。

### ❌ 错误 5｜U-M1：HomePage 有"嵌套重复的 EisenhowerQuadrantCardBuilder 定义"

**实测**：`EisenhowerQuadrantCardBuilder` 全文件只有 **1 处定义（:697）+ 1 处调用（:949）**。`:1309` 是注释。误判。

### ❌ 错误 6｜R-M3：`en_US` 缺 23 条 → 英文用户会看到中文

**实测（全量检索，含引号 / `app.string.` / `$string:` / 字符串拼接四种形式）**：

- 这 23 个键在代码中**出现次数 = 0**
- 反向查"**被代码引用但 en_US 缺翻译**"的键 = **0 个**

**判定：英文环境不会出现中文。** 真实结论恰好相反——`base/string.json` 有 **23 条死条目**该清理。报告"P1 补全英文（2h）"属不必要的工时。

### ⚠️ 错误 7｜B-M7：`parseTaskPriority` 映射"方向相反"

**实测**：两套约定确实不同（`parseTaskPriority` 数字分支为 0基索引 0/1/2，`getPriorityValue` 为权重 1/2/3），但**不是"方向相反"**。且全工程 `getPriorityValue` 只用于排序（HomeViewModel:217/218/277/278），**从未把返回值喂给 `parseTaskPriority`**。

**判定：无实际 bug，降级为"潜在陷阱"**（建议重命名或注释区分两套约定）。

## 三、站得住、该处理的

| 编号 | 问题 | 我的判定 |
|---|---|---|
| **S1** | 无 Release 签名证书 + 路径硬编码 | ✅ **唯一真正的发布阻塞**，与项目自认知一致 |
| **S4** | 四象限拖拽多指触摸竞态 | ✅ **真 bug**。`longPressTimerId` / `touchStartScreenX/Y` / `draggingIndex` 是页面级共享字段，而 `onTouch` 挂在**每张象限卡片**上 → 双指按两张卡会互相覆盖（旧定时器句柄丢失但仍会触发），拖拽指向错误象限且**交换结果会被持久化**。报告的修法（拖拽中忽略新触摸）可行 |
| **S3** | StatsPage 硬编码中文 | ✅ 真。`StatsPage.ets:63-67` 拼中文句喂给 AI → 英文界面下 AI 用中文回复。**采纳报告"改为纯数据结构传给 AI"的建议**（比补资源引用更优） |
| **S5** | 非顶层字段不递归合并 | ⚠️ **现象属实，但性质是设计取舍不是缺陷**。里程碑/L2/L3"随目标整块走"是项目**明确定下的不变式**（改名后的效果是合并语义简单可预测）。报告只看到"可能丢修改"，没看到递归合并需要为子项引入独立 `updatedAt` 语义、且会破坏整块跟随的一致性。**→ 定性为"需产品决策是否升级"，先出方案再决定，不要直接改** |
| **S6** | `nowTimerId` 永不清理 | ⚠️ 报告自己承认"当前因单例生命周期等同进程而无实际泄漏" → **降级**，非严重 |
| **S7** | DeadlineReminderService ~140 行重复 | ✅ 合理（未逐行核，但代码量级可信），纯重构、无功能风险 |
| **R-M1** | 混淆未启用 | ✅ 真。且报告正确注意到混淆规则文件已有 `-keep-property-name` 白名单 |
