# 番茄钟沉浸屏 · 横屏适配方案

> 结论先行：**建议做，而且优先级不低——因为横屏现在不是"不够沉浸"，是功能坏了。**
> 但**不建议强制横屏**，应做「跟随系统方向 + 响应式两栏」。
>
> **2026-09-14 追加**：沉浸模式（3s 自动隐藏控件 + 点击唤回 + 隐藏系统栏）已并入本方案，见 §7；实施顺序见 §8。

## 一、先摆事实：横屏现在到底是"不好看"还是"不能用"

### 1.1 应用的屏幕方向策略（现状）

| 检查项 | 结果 |
|---|---|
| `entry/src/main/module.json5` 是否声明 `orientation` | ❌ **未声明** → 默认 `unspecified`，跟随系统自动旋转 |
| 全工程是否有 `setPreferredOrientation` 调用 | ❌ **0 处** |
| `EntryAbility` 是否做过全屏处理 | ✅ `mainWindow.setWindowLayoutFullScreen(true)`（沉浸屏另有 `expandSafeArea(TOP|BOTTOM)` 把背景铺到状态栏下） |

**推论**：只要用户在系统里开了自动旋转（或平板本来就横着拿），沉浸屏**一定会以横屏渲染**——这不是"要不要支持"的问题，是已经会发生。

### 1.2 竖屏版布局的"高度账单"

`PomodoroImmersiveScreen.ets` · `runningContent()` 的内容高度（按现有常量累加）：

| 元素 | 高度 |
|---|---|
| 阶段药丸（13px + padding 6×2）+ `margin-bottom 26` | 56 |
| 计时环 `width/height 220` | 220 |
| 轮次点行 `height 6` + `margin-top 22` | 28 |
| 任务名 + 提示（`margin-top 18` + 两行文字） | 57 |
| 今日统计 + `margin-bottom 16` | 32 |
| 按钮行 `height 48` + `margin-bottom 80` | 128 |
| **合计** | **≈ 521 vp** |

再叠加顶部关闭栏 `.height(52 + statusBar)` ≈ 90vp，**整屏需要 ≈ 610vp**。

### 1.3 三种屏幕下是否放得下

| 场景 | 可用高度 | 结论 |
|---|---|---|
| 手机竖屏（360×780） | ≈ 690vp | ✅ 正常（余 170vp 给两个 `Blank` 做留白） |
| **手机横屏（780×360）** | **≈ 270vp** | 🔴 **需 521vp，溢出约 250vp** |
| 平板横屏（1280×800） | ≈ 710vp | ⚠️ 放得下，但单列窄内容 → 两侧大片空白，不沉浸 |
| 平板竖屏（800×1280） | ≈ 1190vp | ✅ 正常 |

### 1.4 为什么手机横屏是"坏"而不是"挤"

- `runningContent()` 的根 `Column` 带 `.layoutWeight(1)`（有界），所以两个 `Blank().layoutWeight(1)` 会被压到 **0**，内容**从顶部开始堆**、直接向下溢出；
- 该分支**没有外包 `Scroll`**（只有 `idleContent()` 有），**没有任何滚动兜底**；
- 被挤到屏幕外的正是**最后两个元素**：今日统计 + **暂停 / 停止按钮**（按钮还额外带 `margin-bottom 80`）。

**后果**：横屏下用户**点不到暂停和停止**，只能靠左上角 ✕ 退出（或通知栏）——这是可用性缺陷，不是审美问题。

> 附带说明：`idleContent()` 外面有 `Scroll`，所以待机态横屏是"要滚一下才能按到开始"，属于降级但能用。

## 二、要不要"强制横屏"？

**不建议。** 三个理由：

1. **会打断用户**：躺着单手竖握、或正在输入时突然整屏翻转，是典型的"惊吓式交互"；
2. **平板无意义**：平板横屏是常态，强制等于什么都不做；对竖屏平板反而是打扰；
3. **对抗系统设置**：用户在系统里锁了方向，应用不该绕过他。

**正确做法：尊重系统方向 + 让布局自适应**（窗口宽 > 高即切横版）。这样：
- 手机用户开了自动旋转 → 想横就横，自动变"桌面时钟"；
- 平板横屏 → 直接得到两栏形态；
- 竖屏 → 完全保持现在的观感，零回归。

> 如果你仍希望"手机用户一键横过来"（自动旋转为关闭时），那应该做成**沉浸屏内一个主动的旋转按钮**（用户点击 → `setPreferredOrientation(LANDSCAPE)`，退出时还原），而不是进入就强制。这属于后续可选增强。

## 三、改造方案（响应式两栏）

### 3.1 断点判定

沿用工程既有范式（`AIPage` 的 `onAreaChange` + `isWidePane()`）：

```ts
@Local viewW: number = 0
@Local viewH: number = 0

// 用宽高比而非"宽 > 高"：避免正方形/折叠屏展开瞬间反复抖动
private isLandscape(): boolean {
  return this.viewH > 0 && this.viewW > this.viewH * 1.15
}
```

挂在根 `Stack` 上（它是 `100% × 100%`，宽度由窗口决定，不会因内部布局切换而回环）。

### 3.2 抽可复用子 Builder（关键：不改数据层）

现在 `idleContent()` / `runningContent()` 是两个巨型 `@Builder`，横竖屏要复用同一批零件，先抽出来：

| 抽出的 Builder | 说明 | 是否允许传形参 |
|---|---|---|
| `TimerRing(size)` | 同心圆环 + 时间数字 | ✅ 可传 `size`（纯几何，不参与状态） |
| `PhasePill()` | 阶段药丸（专注中 / 休息中） | ❌ 内部直读 `this.phase/state` |
| `TitleHint()` | 任务名 + 提示语 | ❌ 直读 |
| `RoundDots()` | 轮次点 | ❌ 直读 |
| `TodayStats()` | 今日统计 | ❌ 直读 |
| `Controls()` | 暂停/停止 或 开始下一轮 | ❌ 直读 |

> ⚠️ **必须遵守该文件已有的约定**（文件内 L489-500 注释记录过这个 bug）：`@Builder` 的**基本类型形参是按值传递、不建立状态依赖**——所以状态值**一律在 Builder 内直读 `this.*`**，不能当参数传，否则切换时不刷新。

### 3.3 两种形态

**竖屏（保持现状）**
```
Column { Blank ; PhasePill ; TimerRing(220) ; RoundDots ; TitleHint ; Blank ; TodayStats ; Controls(竖排) }
```

**横屏（新增）**
```
Row(space 32, 垂直居中) {
  TimerRing(220 → 平板可到 280)
  Column(左对齐) { PhasePill ; TitleHint ; RoundDots ; TodayStats ; Controls(横排) }
}
```
- 横屏下 `Controls` 行去掉 `margin-bottom 80`（那是给竖屏底部留的），改 `margin-top 16`；
- 高度上限由环决定（220）< 手机横屏可用 270vp → **放得下**；平板横屏可放大到 280 仍有余量；
- 左上角关闭按钮位置不变（`52 + statusBar` 那条所有形态共用）。

`idleContent()` 同样两栏：左环右「时长胶囊 / 轮次 / 今日统计 / 开始按钮」。

### 3.4 环尺寸建议

| 场景 | 环直径 |
|---|---|
| 手机竖屏 | 220（不变） |
| 手机横屏 | 220（可用高 270，留 25 上下边距） |
| 平板横屏 | 260~280（按 `min(可用高 - 48, 可用宽 × 0.32)` 收敛） |

## 六、结论

| 问题 | 回答 |
|---|---|
| 有必要做吗？ | **有必要**。手机横屏现在是"暂停/停止点不到"的功能缺陷；平板横屏则是明显的空间浪费。 |

## 七、沉浸模式（追加需求）

> 需求：running 态 3 秒无交互 → 除时间外全部控件淡出；点击屏幕任意位置 → 控件回来；状态栏与底部导航栏必须隐藏。

### 7.1 赞成，而且它顺带解决一个隐患

番茄钟的本质是"陪用户 25 分钟"，控件长期挂着本身就是干扰。除此之外还有个**被忽略的收益：消除误触**——现在 ✕ 在左上角、暂停/停止在底部，长时间亮屏、躺着或手边放着时，很容易被误碰（尤其"停止"会丢弃当前轮次）。

### 7.2 只在 `running` 态自动隐藏

| state | 自动隐藏 | 原因 |
|---|---|---|
| `idle` | ❌ | 用户要选时长、点开始 |
| `running` | ✅ | 目标态（专注 / 休息都适用） |
| `paused` | ❌ | 用户正在做决定，"继续 / 停止"必须看得见 |

### 7.3 实现方式：**淡出，而不是从结构里移除**（关键取舍）

现有竖屏结构是 `Blank(1) │ 药丸 │ 环 │ 轮次点 │ 名称 │ Blank(1) │ 统计 │ 按钮`；横屏是两栏。

- 若用 `if` 把元素从组件树上摘掉 → 两个 `Blank` 重新分配 → **环会跳到新的居中位置**；横屏下右栏塌陷 → **环横向跳动**；
- 改用 `opacity(0)` + `.hitTestBehavior(HitTestMode.None)`（不可点）+ 250ms 隐式动画 → **布局零位移**，实现最简、风险最低。

> ⚠️ 用 `HitTestMode.None` **而不是 `Block`**：`Block` 会连祖先节点一起挡掉触摸测试（本日 `TaskDetailPage` 刚踩过，已写入项目工程约定）。

**代价**：隐藏后控件仍占位，环停在原位置而非绝对居中。若要"环绝对居中"的终极构图，可在淡出后追加一步 `offset` 平移动画（可选）。

### 7.4 "点击唤回"的 4 个必须处理点

1. **挂载位置**：根 `Stack` 的 `.onClick()`。ArkUI 中子组件命中时父级 onClick 不触发 → 点按钮/胶囊仍是各自功能，点空白才是"唤出"。
2. **用 `onTouch` 重置计时器**（不能只在"唤回"时重置）：否则用户正在按按钮的过程中，控件会突然淡出。
3. **`showStopSheet === true` 时暂停自动隐藏**：否则停止确认面板一关，底下一片空白。
4. **定时器必须在 `aboutToDisappear()` 清掉**：照抄该文件既有的 `tickCbId / stateCbId / breathAnimTimer` 清理范式，避免"已退出还在跑"的泄漏。

3 秒是视频播放器通用值（3~5s），**不建议做成设置项**——这一层不需要配置。

### 7.5 系统栏：API 已核实 + 两个坑

**API**：`window.Window.setWindowSystemBarEnable(names: Array<'status'|'navigation'>)`
- `[]` → 状态栏 + 导航栏**全部隐藏**；`['status','navigation']` → 全部显示（API 9+，官方最佳实践《Immersive Page Development Practice》即用此法）。

**坑 1：不要照抄官方示例。** 官方示例在还原时同时调用了 `setWindowLayoutFullScreen(false)`；而本工程 `EntryAbility.initWindowInsets()` 在启动时就全局设置了 `setWindowLayoutFullScreen(true)`。
→ **我们只切换"系统栏可见性"，绝不触碰 layoutFullScreen 标志**，否则会破坏全应用的避让逻辑。

**坑 2（最重要）：不要把用户困住。** 两条系统栏都隐藏后，退出路径只剩"点屏幕唤出 ✕"（侧滑返回是否仍可用取决于系统手势实现，**无法保证**）。
→ 因此 **"点击唤回"不是锦上添花，它是本次改动的安全网**，必须与"隐藏"成对实现，不能只做隐藏。

**双保险（防止"应用永久没有状态栏"）**：
1. `aboutToDisappear()` **无条件**恢复 `['status','navigation']` —— 覆盖 ✕ / 停止 / 页面退出 / 外层 `if` 条件变化所有路径；
2. `EntryAbility` 启动时**再无条件恢复一次**（自愈）—— 万一进程在隐藏态被杀或崩溃，下次启动自动恢复，不会留下"应用没有状态栏"的诡异故障。

**两个小细节**：
- 隐藏状态栏后，顶部栏 `.height(52 + safeAreaHelper.statusBar)` 的让位会成为多余留白（关闭按钮下移）；隐藏态下控件本就不可见，影响很小，若要精细可让隐藏态取 0；
- 横屏下刘海位于侧边，官方最佳实践建议用 `display.getCutoutInfo()` 做避让 —— 沉浸态控件全隐藏，只有环与数字，一般不会被切，**放二期**。

### 7.6 可选搭档：屏幕常亮（`setWindowKeepScreenOn`）

控件与系统栏都隐藏后，用户很可能把手机立在桌上当"桌面时钟"，此时**自动息屏会直接毁掉这个场景**。建议一并加，但必须在**五处**还原：停止 / ✕退出 / 暂停超时 / `aboutToDisappear` / `onBackground`（任一处漏掉都会留下耗电陷阱）。**是否纳入本次由你决定。**

**⚠️ 实施中修正的一处自身缺陷（值得记档）**

`HitTestMode.None` 只让**自身**不参与触摸测试，**子节点仍可命中** → 控件淡出后，暂停/停止/✕ 会变成**隐形热区**：点击既会误触发按钮，又抢走"点击唤回"的那一次点击（表现就是"点了没反应"或"点了直接暂停"）。

修复：在**含可交互子节点的两个容器**（顶栏 Row、按钮行 Row）上额外加 `.enabled(this.chromeVisible)` —— `enabled(false)` 让整棵子树失效，且**不阻断祖先节点**，点击仍能到达根 `Stack` 完成唤回。

> 为什么不用别的方案：API 12 没有 `BLOCK_DESCENDANTS`；而 `Block` 会连祖先一起挡掉（正是本日 `TaskDetailPage` 踩过的坑），会导致唤回失效。**`enabled` 是这里唯一正确的解。**

## 九、落地记录（步骤 ②：横屏两栏）

> ⚠️ **本节与第十节已被 §11 推翻并回滚**（2026-09-14）。保留原文是为了记录踩过的两个坑，**请以 §11 为最终方案**。

### 9.1 先修一个前提：`unspecified` ≠ "跟随传感器"

官方《module.json5 配置文件》原文：`orientation` 缺省值为 **`unspecified` = "未指定方向，由系统自动判断显示方向"**。
而官方《多设备窗口形态》明确建议：**"若应用为可旋转应用，建议配置 `auto_rotation_restricted` 为默认旋转策略"**。

也就是说：本项目未声明 `orientation`，系统可能把这个 App **判为竖屏应用** → **手机横拿时根本不旋转**，"横屏版式"永远看不到。

**修法（最小侵入）**：不改 `module.json5`（那会改变全应用行为），只在**沉浸屏生命周期内**用窗口级 API 放开：

```ts
// 进入沉浸屏：跟随传感器旋转，但尊重控制中心的"旋转锁定"开关
win.setPreferredOrientation(window.Orientation.AUTO_ROTATION_RESTRICTED)
// 退出沉浸屏：还原为应用默认策略
win.setPreferredOrientation(window.Orientation.UNSPECIFIED)
```

选 `RESTRICTED` 变体而不是 `AUTO_ROTATION`：**用户在控制中心锁了旋转就尊重他，不强行转**。

### 9.2 实现方式修正：不抽 6 个 Builder，改用一个 `Flex` 切方向（风险更小）

实施时发现 §3.2 的方案可以大幅简化 —— 关键在于**两个分组在竖屏下的先后顺序，在横屏下变成左右两栏后依然一致**：

| 分组 | 内容 | 竖屏 | 横屏 |
|---|---|---|---|
| **A** | 阶段药丸 + 计时环（待机态：计时环） | 上方 | 左栏 |
| **B** | 轮次点 / 任务名+提示 / 今日统计 / 操作按钮 | 下方 | 右栏 |

因此**不需要重排任何节点、不需要抽 6 个 Builder**，只要：

```ts
Flex({
  direction: this.isLandscape() ? FlexDirection.Row : FlexDirection.Column,
  justifyContent: FlexAlign.Center,
  alignItems: ItemAlign.Center
}) {
  if (!this.isLandscape()) { Blank().layoutWeight(1) }   // 竖屏的均分留白；横屏不能有（Row 里 Blank 会横抢宽度）
  Column() { /* A 组 */ }
  Column() { /* B 组 */ }.layoutWeight(1)                 // 竖屏吃满剩余高度、横屏吃满剩余宽度
}
```

**优势**：原有内联代码可**逐字保留**（脚本按行范围搬迁 + 断言），竖屏回归面 ≈ 0；只把 5 处"与方向相关"的间距改成三元：
药丸 `margin-bottom 26→8`、轮次点 `margin-top 22→0`、任务名 `padding 40→0 / margin-top 18→0`、按钮行 `margin-bottom 80→12`（待机态另加胶囊间距 `20→12`）。

**一处保真度修正**：待机态的留白原本是 `Blank(1) : Blank(0.4)`（71% : 29%）。若 B 组直接给 `layoutWeight(1)` 会变成 50 : 50、整块构图上移 → 故写成 `.layoutWeight(this.isLandscape() ? 1 : 0.4)` 保留原比例。（运行态原本就是 1 : 1，无需处理。）

### 9.3 横屏后的空间账（手机 360×780 → 横屏 780×360）

| 项 | 竖屏 | 横屏 |
|---|---|---|
| 顶部关闭栏 | 52 + statusBar ≈ 90 | 同（状态栏隐藏后系统避让区会缩到 0，`safeAreaHelper` 会自动把这段让位去掉） |
| 可用高度 | ≈ 690 | ≈ 270 |
| A 组高度 | 药丸 56 + 环 220 = 276 | 药丸 30+8 + 环 220 = **258 ✓ 放得下** |
| B 组高度 | 约 200 | 约 200 ✓（垂直居中） |
| 结果 | ✅ | ✅ 环在左、信息与控件在右，两侧不再拥挤 |

平板横屏（1280×800）：可用高 ≈710，两栏之间留白更宽松，环保持 220（如需更像桌面时钟可放大到 260~280 单独排期）。

### 9.4 待机态（idle）横屏

同样改为两栏：**A = 待机环**（呼吸外环 + 轨道 + 时间 + "准备专注"）、**B = 任务名 / 时长胶囊 / 轮次 / 今日统计 / 开始按钮**。
仍保留在外层 `Scroll` 内 —— B 组内容略高（两行时长胶囊），横屏若有溢出可滚动兜底，不会出现"按钮点不到"。

## 十、隐藏控件后的构图修正（用户截图反馈）

> ⚠️ **本节方案已回滚**（见 §11）：两拍收拢（`chromeCollapsed`）在实测中出现"内容掉到底部"，用户判定"不行，不折腾了"。最终采用 §11 的极简横屏。

### 10.1 现象

横屏下控件淡出后，画面变成：**计时环被挤在左下角、环底贴着屏幕边、右侧一整片空白**。用户反馈"很突兀"。

### 10.2 根因（三个叠加）

| # | 问题 | 原因 |
|---|---|---|
| 1 | 环被挤到最左 | B 组虽然 `opacity: 0`，但**仍然占满 `layoutWeight(1)` 的剩余宽度** → A 组被推到最左边 |
| 2 | 环底贴边、像被切掉 | A 组高度 = 药丸 38 + 环 220 = **258vp ≈ 横屏可用高度 259vp** → 几乎没有余量，环底正好压在屏幕边缘 |
| 3 | 右侧一片空 | 同上：B 组不可见却占据全部右侧空间 |

**本质**：`opacity(0)` 只解决"看不见"，**不解决"还占着地方"**。沉浸态的构图应该是"环独占整屏、居中"，而当时只是"元素变透明"。

### 10.3 修法：两拍收拢（先淡出，再归位）

新增 `@Local chromeCollapsed`，**比 `chromeVisible` 晚一个淡出时长**：

```ts
private hideChrome(): void {
  this.chromeVisible = false                     // 第 1 拍：淡出（布局不动，元素原地消失）
  this.chromeCollapseTimer = setTimeout((): void => {
    if (!this.chromeVisible) {                    // 淡出期间可能已被唤回 → 不能再收拢
      animateTo({ duration: 250, curve: Curve.EaseOut }, (): void => {
        this.chromeCollapsed = true               // 第 2 拍：收拢占位 + 环滑向正中
      })
    }
  }, CHROME_FADE_MILLIS)
}
```

收拢态做三件事：

| 对象 | 处理 |
|---|---|
| B 组（轮次点/任务名/统计/按钮） | `.visibility(this.chromeCollapsed ? Visibility.None : Visibility.Visible)` —— **撤掉占位** |
| 阶段药丸 | 同样 `Visibility.None`（否则那 38vp 会把环往下压、无法真正居中） |
| A 组 | `.layoutWeight(this.chromeCollapsed ? 1 : 0)` + `.justifyContent(FlexAlign.Center)` —— **吃满整屏，环落在正中** |
| 竖屏的留白 `Blank` | 收拢态不渲染（`!this.isLandscape() && !this.chromeCollapsed`） |

**为什么用 `Visibility` 而不是 `if` 摘除节点**：`visibility` 是属性变更，能与 `animateTo` 同批处理、并让 A 的几何变化被平滑插值；`if` 摘除则无法参与动画。另外它不需要重新缩进上百行 JSX —— 内联代码仍逐字保留。

**关键点**：收拢发生在淡出**之后**，此时 B 组与药丸已经全透明，**撤占位没有任何视觉痕迹**；用户唯一感知到的"运动"是**计时环滑到画面正中**。这就是"不突兀"的来源。

唤回方向对称：`expandChrome()` 把"取消收拢"包在 `animateTo` 里（环滑回原位），同时 `chromeVisible = true` 触发各元素自身的 250ms 淡入。

### 10.4 效果

| 状态 | 构图 |
|---|---|
| 控件可见 | 竖屏单列 / 横屏两栏（环在左、信息与控件在右） |
| **控件隐藏（沉浸态）** | **计时环独占整屏、水平垂直双居中**，其余全部撤出 —— 竖屏与横屏一致 |

### 10.5 未做（可选）

- 平板横屏收拢后，环仍为 220vp；若要更像"桌面时钟"可放大到 260~300（需把 4 处 `220` 换成 `ringSize()` getter，单独排期）。
- 收拢态可再加一层极淡的呼吸/刻度动画增加"活感"（当前为完全静止）。

## 十一、最终方案：极简横屏（回滚两栏，2026-09-14 定案）

### 11.1 用户决定

> "不行，现在内容完全掉下去了，横屏下都无法显示内容了，**不行这个就不做了**，或者简单一点，**横屏就给暂停和开始两个按钮，更多的回到竖屏**。"

**采纳**：放弃横屏信息平铺，横屏只保留"**计时环 + 按钮**"，其余信息一律回竖屏查看。

### 11.2 真凶：`Blank` 在 `Flex` 里会无视 `layoutWeight`

"内容完全掉下去"的根因不是间距、也不是 `animateTo`，而是——

> **`Blank` 自身的语义是"自动填满容器剩余空间"。一旦把它放进 `Flex`，这个语义会压过 `layoutWeight`，把全部余量吃光 → 后续内容被顶到最底部。**

上一轮为了"一个组件同时支持竖排/横排"而把 `Column` 换成 `Flex`，`Blank` 的行为随之改变 → 竖屏（待机/运行）内容整体沉底。

**教训（已写入项目工程约定）**：需要"竖排/横排两种排布"时，**不要用 `Flex` 切 direction**；用 `if (方向) { Row {...} } else { Column {...} }`。`layoutWeight` 与 `Blank` 的语义只在 `Row`/`Column` 下是稳定可预期的。

### 11.3 最终实现

| 版式 | 内容 |
|---|---|
| **竖屏** | 与改造前**逐字一致**（`Column` + 完整信息：药丸/环/轮次点/任务名/统计/按钮；待机含时长胶囊） |
| **横屏 · 待机** | `idleLandscape()`：计时环 + 「开始专注」按钮 |
| **横屏 · 运行/暂停** | `runningLandscape()`：计时环 + 「暂停/继续」「停止」 |

分流点在 `build()`：

```ts
if (this.state === 'idle') {
  if (this.isLandscape()) { this.idleLandscape() } else { this.idleContent() }
} else {
  if (this.isLandscape()) { this.runningLandscape() } else { this.runningContent() }
}
```

**改回 `Column` 后，竖屏恢复原始行为**（`Blank(1) : Blank(1)` / `Blank(1) : Blank(0.4)` 的留白比例照旧）。

### 11.4 横屏的两个关键设计

**① 环直径按可用高度收敛**（否则 220 环 + 按钮在手机横屏会溢出）：

```ts
private landscapeRingSize(): number {
  const topBar: number = 52 + safeAreaHelper.statusBar
  const avail: number = this.viewH - topBar - 66 - 32   // 66 = 按钮行 48 + 间距 18；32 = 上下呼吸
  return Math.max(LANDSCAPE_RING_MIN, Math.min(LANDSCAPE_RING_MAX, avail))
}
// 手机横屏：360 − 90 − 98 = 172 → 取 172（上限 180）；下限 120 兜底
```

**② 时间字号随环直径等比缩放**：`Math.round(size * 0.2545)` → 220 → **56vp（与改造前完全一致）**，180 → 46vp。

**③ 抽出两个环 Builder**（竖屏/横屏共用，避免重复）：`idleRing(size)`、`runningRing(size)`；竖屏传 `PORTRAIT_RING_SIZE`(220)。

**④ 停止二次确认抽成 `askStopConfirm()`**，竖屏横屏共用（原先内联在竖屏按钮的 onClick 里）。

### 11.5 同时回滚的内容

- `Flex` → `Column`（两处）
- 两拍收拢机制整体删除：`chromeCollapsed`、`chromeCollapseTimer`、`hideChrome()`、`expandChrome()`、`animateTo`、`Visibility.None` 全部撤掉 → 回到**单拍淡出**（简洁、无位移）
- 为横屏准备的 9 处三元间距全部还原为常量（药丸 26 / 轮次点 22 / 任务名 padding40·margin18 / 按钮行 80 / 待机胶囊 20 等）

**保留**：`isLandscape()`（宽高比 1.15 判定）、`viewW/viewH` + `onAreaChange`、`applyOrientation()`（`AUTO_ROTATION_RESTRICTED`，让手机真的能转）。

## 十三、计时环极简化：对标业界（2026-09-14 定案）

### 13.1 用户反馈

> "感觉这个太丑了，一定要简约美观的感觉……或者你看看别人家怎么做的，借鉴一下。"

上一轮只解决了色相，**"丑"的根源在几何结构**。

### 13.2 现状为什么丑：三层同心 + 两个多余装饰

改造前 `idleRing` / `runningRing` 的结构：

| 层 | 参数 | 问题 |
|---|---|---|
| 呼吸外环（仅待机） | `Circle(size + 24)`，`strokeWidth 1` | 悬在轨道外侧 24vp 的**独立细圈** → 形成"两个同心圆错位"，是"别扭感"最直接的来源 |
| **柔光层** | `strokeWidth 22`，低透明度同色 | 宽度是进度弧（10）的 **2.2 倍** → 环外糊出一圈巨大毛边，"糊成一团"的根源 |
| 轨道层 | `strokeWidth 10` | 与进度同宽 ✓ |
| 进度层 | `strokeWidth 10` | ✓ |
| 环内时间 | `size × 0.2545`（220 → **56vp**） | 占环直径 25%，环内几乎没有留白，12vp 副标题被巨字压住 |

### 13.3 业界怎么做（本轮调研）

查了 Focus To-Do / iOS 计时器 / SwiftUI 计时器范例 / 多个开源番茄钟实现，**共同语言高度一致**：

| 维度 | 业界做法 | 本项目改造后 |
|---|---|---|
| 层数 | **只有 2 层**：muted 轨道 + 彩色进度弧（从无第三层装饰） | 2 层 ✓ |
| 线宽 | 直径的 4~5%（SwiftUI 范例：280pt 环 → 12~15pt） | 8vp / 220 = **3.6%**（偏轻一侧） |
| 轨道 / 进度线宽 | **完全相同**（进度精确覆盖轨道） | 相同 ✓ |
| 时间字号 | 直径的 0.17~0.20 | **0.21**（取可读性上限） |
| 数字字体 | **等宽**，防数字跳动 | `monospace` ✓（原有） |
| 起点 | 12 点方向 | ArkUI Progress Ring 默认即 12 点 ✓ |
| 待机态 | 显示完整淡轨道，无额外装饰 | 同 ✓ |

### 13.4 落地改动（`PomodoroImmersiveScreen.ets`）

| # | 改动 |
|---|---|
| 1 | **删除待机的"呼吸外环"**（`Circle(size + 24)`） |

| 3 | 新增常量 `RING_STROKE = 8`，轨道与进度统一引用（避免下次又改出差异线宽） |

### 13.5 两个刻意**不做**的决定

- **不做圆头进度弧**：ArkUI `Progress` 的 `ProgressStyleOptions` 只有 `strokeWidth` / `enableSmoothEffect`，**没有 `lineCap`**。要圆头必须用 `Circle` + `strokeDashArray` 自绘，而本项目自绘矢量已踩过"`Path.commands` / `strokeWidth` 单位是 px 而非 vp"的坑（见 `PomodoroGlyph` 文件头）。8vp 细线上平头与圆头差异极小，**不值得为此冒险**。
- **不做 `enableSmoothEffect`**：会让进度变化产生过渡延迟，与"暂停时一眼可见"（进度层降透明度）的设计意图冲突，也削弱倒计时的精准感。
