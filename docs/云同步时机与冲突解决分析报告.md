# 云同步「时机 + 冲突解决」分析报告

> 2026-10-13。**逐行核实当前实现**（`CloudSyncService` 941 行 / `SettingsViewModel` / `EntryAbility` / `MainTab` / `PersistHelper`），非凭印象。
> 用户诉求：把「打开软件 / 热启动 / 多设备」的自动同步时机与冲突解决讲清，并评估"云库加自增计数字段、不一致就云端覆盖本地"这一方案。

## 一、现状：触发时机全景（8 个入口）

| # | 时机 | 入口（证据） | 防抖/节流 | 方向 |
|---|---|---|---|---|
| 1 | **冷启动** | `MainTab.initAndRestoreMigration` → `settingsVM.init()` → `syncNowDetached('cold-start')` | 无 | 双向 merge |
| 2 | **登录完成** | `SettingsViewModel.applyLoginResult:1029` → `syncNowDetached('after-login')` | 无 | 双向 merge（并集） |
| 3 | **回前台** | `EntryAbility.onForeground:488-489` → `notifyCloudReady()` + `triggerSync()` | 1s 防抖 | 双向 merge |
| 4 | **热启动**（点通知 / 多端流转） | `EntryAbility.onNewWant:161` → `triggerSync()` | 1s 防抖 + **30s 跨次节流** | 双向 merge |
| 5 | **本机数据变更** | `PersistHelper.onScheduleFire` → `markSyncNeeded()` → 触发 merge | **2s 防抖** + 持久化脏标记 | 上传为主 |

| 7 | **就绪补跑** | `notifyCloudReady()` → `syncNowDetached('ready-retry')` | 见 §三-1 | 双向 merge |
| 8 | **退出登录前** | `SettingsViewModel:1144` 附近 → `syncNow('pre-logout')` | 无 | 预上传 |

**统一入口**：所有路径都收敛到 `triggerSync()`（防抖 1s）或 `syncNow()`（即时）——**禁止任何绕过入口的裸上传/下载**（代码注释明示）。

### ❌ 关键缺失（这就是"多端不无感"的原因）

| 缺失 | 影响 |
|---|---|
| **未使用 CloudDB 实时监听**（全工程无 `addSnapshotListener`） | 服务端不会主动推变更 |
| **无周期性拉取**（同步链路里无 `setInterval`） | 前台不会定时复查 |
| ⇒ 两台设备**同时开着**时：A 改了，B **不会**自动刷新 ✗ | 必须靠"切后台再回前台 / 重启 / 手动点" |

> 好消息：**UI 层的"无感刷新"链路是通的** —— 云端落地时 `applyCloudSnapshot` 会逐目标广播 `GOAL_PROGRESS_CHANGED`，直读 `liveGoals` 的页面（首页/统计/路线）自动刷新，持副本的页面（目标详情/历史）靠订阅 ✔。
> **瓶颈不在 UI，而在"何时去拉"**。

## 二、现状：冲突解决（4 层）

| 层 | 规则 | 位置 |
|---|---|---|
| ① 准入判据 | **等值判断**：`云端 updatedAt !== 本机水位` **或** 本地 `dirty` 才合并；都用 `===` 而非大小比较（**刻意免疫跨设备时钟偏差**） | `CloudSyncService:263-271` |
| ② 两个数组 | `goals` / `taskList` **各自**按 **id 条目级并集**：同 id → **墓碑 OR**（任一方 `isDeleted` 则保持删除）+ 条目 `updatedAt` 大者胜；**完全相等或双方都缺失 → 本地优先**；非数组兄弟字段（version/filterCategory）取云端 | `mergeTopLevelArray:476` / `pickWinner:546` |
| ③ 完成事实对齐 | `reconcileCompletionFacts`：把同一完成事实的**两份副本**（`goals[G].tasks[T].status + steps[].isCompleted` ↔ `taskList[T].isCompleted`）对齐 + 重算派生 `progress`；**纯函数、不改任何 updatedAt** | `:653` |
| ④ 其它段 | `settings` 本地优先 / `profile` 云端优先 | `runMergeOnce:290-291` |

**上传判据**：合并结果 vs 云端做**指纹比对**（4 段 canonical 哈希 + 长度），不同才上传 ⇒ 两端自动收敛 ✔（`payloadFingerprint:863`）

## 三、现有缺口（3 个，均有代码证据）

### 1. 🔴 已修（今天）：就绪 gate 竞态滞留 → 自动同步永不发生
`isReadyToSync()` 需同时满足「CloudDB 已初始化」+「快照已注册」，而这两件事分别回调 `notifyCloudReady()`，**谁先到另一个就还没就绪，两边都 return** ⇒ `pendingReadySync` 永久滞留 ⇒ 表现为"**必须手动点立即同步**"。
→ 已改为**退避重试自愈**（500ms × ≤20 次）✔（提交 `155c2b2`）

### 2. 🔴 **条目内部原子覆盖 ⇒ 丢更新**（代码注释自己承认）
`pickWinner:644` 原文：
> 「⚠️ 本方法**不解决**"整块 LWW 丢更新"（平板改个名字 `G.updatedAt` 变大即**整块覆盖手机勾的完成态**）」

⇒ 合并粒度只到**顶层条目**（一个 goal / 一个 todo），**条目内部（tasks / steps）是原子覆盖** ✗
⇒ 场景：手机勾了「目标 G」下某任务的步骤，平板改了「目标 G」的名字 ⇒ G 的 `updatedAt` 在平板变大 ⇒ 整条 G 覆盖手机 ⇒ **步骤勾选被抹掉**（部分场景由 ③ 的完成事实对齐兜住，但不全）

### 3. 🟡 前台不复查（§一 的缺失）
前台停留期间不做任何云端复查 ⇒ 多端"无感"不成立。

## 四、你的方案评估：「云库加自增字段，数字不一致就云端覆盖本地」

**结论：方向对了一半 —— "用版本信号做准入"很好，但"不一致就云端覆盖本地"是危险动作，不能照做。**

| 你的设想 | 评估 |
|---|---|
| 每次改数据给一个计数 +1 | ✅ **对**：单调计数器**免疫时钟偏差**，正是当前"等值判据"想绕开的问题 |
| 数字不一致 ⇒ 需要同步 | ✅ **对**：这是比"等值时间戳"更强的信号 |
| **数字不一致 ⇒ 云端覆盖本地** | ❌ **危险**，三点理由见下 |
| 覆盖也包含删除操作 | ⚠️ 方向**单向正确**：云端删了 → 本地应删 ✔；但**本地新增/本地改动会被云端旧版抹掉** ✗ |

### ❌ 为什么"覆盖"不行

1. **会丢本机未上传的改动**：本机刚勾了步骤（`dirty` 还没上传），另一端也改了别的 ⇒ 数字不一致 ⇒ 云端覆盖 ⇒ **本机改动消失** ✗。正确顺序必须是"**先上传本机 → 再合并**"。
2. **对"本地独有数据"会误删**：覆盖 = 云端是唯一真相 ⇒ 本机新建、云端还没有的目标/任务会被删掉 ✗（当前实现刻意做**并集**就是为了这个）。
3. **计数器放"整条记录"上表达不了"哪一条变了"** ⇒ 仍要条目级裁决 ⇒ **解决不了缺口 2（条目内部原子覆盖）**，那是当前最痛的点。
4. **并发 +1 会碰撞**：两端同时 +1 ⇒ 都是 N+1 但内容不同 ⇒ "数字相同"被误判为一致 ⇒ **漏同步** ✗（时间戳至少有序，计数器会撞）。

### ✅ 可以吸收的部分（替换成更强的形式）

| 吸收点 | 更稳的形式 |
|---|---|
| 用版本信号做准入 | 用**内容指纹**（工程里已有 `payloadFingerprint`）替代"等值 `updatedAt`"：**指纹不同就必须合并** ⇒ 免时钟、免碰撞 ✔ |
| 表达"变了" | 指纹天然表达"内容变了没有"，且**不会漏判**（计数器会） |
| 删除语义 | **保留现有墓碑 OR**（删得掉、且不会被旧版"复活"）✔，不要退回整包覆盖 |
| 若要表达"哪一条变了" | 版本号要**下沉到条目级**（goal/todo 各带 `rev`），再下沉到子条目（task/step）才能根治缺口 2 —— 成本高，建议分期 |

## 五、建议方案（分期，供你拍板）

### P0 ·「多端无感刷新」——补上"何时去拉"（收益最大、风险最低）

三选一（我建议 a，或 a+b）：

| 选项 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **(a) 前台轻量轮询**（推荐） | 前台每 60~120s **只比对云端记录的 `updatedAt`/指纹**，变了才 merge；不变则零写入 | 极低（一次轻查询/分钟） | 低 |
| (b) CloudDB 实时监听 | `addSnapshotListener` 订阅该用户记录 ⇒ 真正的秒级无感 | 需确认 CloudDB 支持与配额/计费 | ⚠️ **未知**，需查官方文档 |
| (c) 仅靠现有事件 | 冷启动 / 回前台 / 热启动 | 0 | 同前：多端同前台不刷新 ✗ |

> 另需补一个**细节改进**：把"回前台"的 merge 从"仅依赖 `notifyCloudReady` 补跑"改成**无条件触发一次**（回前台是天然的复查时机）。

### P1 · 准入判据升级为「内容指纹比对」
- `lastSyncTime` 水位语义**保持**（它已在用），但**准入改为**：`云端指纹 !== 本机上次指纹` 或 `dirty` ⇒ 才 merge
- 好处：彻底免疫时钟；避免"水位恰好相等但内容不同"的漏判

### P2 · 根治「条目内部原子覆盖」（缺口 2）
- 把 `pickWinner` 从"整条 goal 原子"拆成：**goal 元信息（name/desc/category/deadline）** 与 **tasks 数组** **分开裁决**；tasks 再按 `task.id` 合并、steps 按 `step.id` 合并
- 必须配套：`reconcileCompletionFacts` 与指纹收敛的回归（否则会来回上传）
- ⚠️ 工作量最大、最易出回归 ⇒ **建议 P0/P1 稳定后再动**，并先写双设备回归用例

## 七、给"改完之后"的验收用例（双设备）

| # | 场景 | 期望 |

| 1 | A 改数据 → B **前台停留** | P0 后：≤ 轮询周期（或监听秒级）自动出现 |
