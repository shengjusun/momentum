## 二、根因：两次同源的"旧文件覆盖"

### 2.1 第一次：2026-09-29 `commit 3482060`

该提交的说明只写了"修复 AiGeneratedTask 新签名调用点 + 补齐 77 个缺失资源 key"，但实际改动为
`GoalDetailPage.ets 975 行 / RoutePage.ets 610 行 / GoalHistoryPage.ets 16 行 / 3×string.json`（净删除 8623 行）。

**证据（`git show 3482060 -- GoalHistoryPage.ets`）**：它把演进过的代码换回了旧写法——

| 项目 | 09-18 版（演进后） | 3482060（旧版） |
|---|---|---|
| 读取列表 | `routeVM.liveGoals`（派生视图） | `routeVM.goals`（直读底层） |
| 尺寸常量 | `DimensConstants.RADIUS_XS / RADIUS_L` | 魔数 `4` / `16` |
| 依赖 | `SafeAreaHelper` / `MotionConstants` | 引用被删除 |
| 品牌值 | `app_name=起势`、`login_brand_name_cn=起势` | `app_name=Momentum`、`login_brand_name_cn=势能` |
| 模板残留 | 已清理 | 退回 `module_desc = MyApplication 主模块` |

⇒ 作者当时只发现"77 个 key 缺失"就顺手补齐，**旧代码的回退被一起提交了**，导致工程护栏至今带 29 项红灯。

### 2.2 第二次：2026-10-09 09:22:15~16（今天这次报错）

三个 `string.json` 的 mtime **精确到同一微秒**（`2026-10-09 09:22:16.015105000`）⇒ 一次批量写入；`SafeUtils.ets` 为 `09:22:15.079764300`。

- 三语言各**丢 80 个 key、新增 0 个**；同 key 值只改了 3 处，**全是退回旧值**（`app_name` 起势→Momentum、`login_brand_name_cn` 起势→**势能**、`module_desc` →MyApplication 主模块）——**与 2.1 的旧快照指纹完全一致 ⇒ 两次事故同源**。
- `SafeUtils.ets` 与 `3e14aa4`（2026-09-11）**逐字节相同**（1187/28 行）⇒ 整文件退回旧版。
- `GoalDetailPage.ets` / `RoutePage.ets` 相对 HEAD 只差 **+8 / +4 字节** ⇒ 3 处复活了已废除的第 7 参 `completedSteps`（现 `TaskModels.ets:202` 的第 7 参是 `plannedTime: Timestamp`，传 `[]` 即类型错）。

**决定性校验**：`缺失引用 key 集合 == HEAD 有而工作区丢失的 key 集合`（**80 == 80**，无交集差），且 HEAD 三语言能全部命中 ⇒ 复原 HEAD 即可消除 84 个资源类报错。

### 2.3 覆盖来源

磁盘全盘搜索无同源副本（`.workbuddy/_origin.txt`），工作区内容也不等于任何历史提交 ⇒ 是**外部把旧内容写回**，且至少两个年代（`SafeUtils` 来自 09-11、`string.json` 来自 09-29 前）。建议排查：DevEco **Local History / 文件还原**、项目目录是否被**云盘/备份工具同步**、是否从旧 zip 拷过文件。
