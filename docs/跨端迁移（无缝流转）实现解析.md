# 跨端迁移（无缝流转）实现解析 —— 以「起势 / Momentum」为例

> 面向要在**另一个 App** 里复刻该能力的开发者。
> 全文基于本工程源码逐行核实（EntryAbility / RouterManager / MainTab / module.json5），非泛泛教程。

---

## 1. 系统行为：一次流转到底发生了什么

用户在源设备上通过系统入口（控制中心 / 超级终端 / 任务卡片的流转按钮）发起迁移后：

```
源设备                                目标设备
──────                                ──────
系统回调 UIAbility.onContinue(wantParam)
  → 应用把"当前界面在哪"打包进 wantParam
  → 返回 AGREE
        └────────── 系统传输 Want ──────────►  目标设备拉起/唤醒本应用
                                              若进程不在：onCreate + onWindowStageRestore
                                              若进程还在：onNewWant（热启动）
                                              应用解析 Want → 恢复到同一界面
```

两个前提（缺一不可）：

1. `module.json5` 的 ability 上声明 **`"continuable": true`**；
2. 两台设备登录**同一华为帐号**（系统级要求，代码管不了）。

## 2. 本工程的实现总览

| 文件 | 职责 |
|---|---|
| `module.json5` | `"continuable": true`（能力开关） |
| `EntryAbility.onContinue()` | **源端**：打包当前界面（路由名 + 参数 + Tab 下标） |
| `EntryAbility.onCreate/onNewWant` | **目的端**：从 Want 解析迁移载荷（冷/热启动都走） |
| `EntryAbility.onWindowStageRestore` | 接续冷启动走的是 **Restore** 而非 Create，两处必须同样初始化窗口 |
| `RouterManager` | 载荷单例 + 恢复执行（切 Tab + pushPath）+ 深链竞态协调 |
| `MainTab.initAndRestoreMigration` | 目的端入口：先 init 三个 VM，**再**延迟恢复路由 |

载荷结构（刻意保持极小）：

```ts
interface MigrationPayload {
  routeName: string   // 目的端要打开的页面，如 'GoalDetailPage'
  param: string       // 该页面参数序列化后的 JSON，如 {"id":"goal_xxx"}
  tabIndex: number    // 底部 Tab 下标
}
```

⚠️ **数据不走迁移通道**。只传"在哪"，不传"内容"——目标设备上的数据由本地 VM（+ 云同步）自己加载。
这是本设计最关键的一条原则：载荷越小越稳，也不把用户数据暴露在系统通道里。

## 3. 源端：`onContinue` 逐行拆解

```ts
onContinue(wantParam: Record<string, Object>): AbilityConstant.OnContinueResult {
  // ① 声明"页面栈不由系统恢复，应用自己管导航"
  wantParam[wantConstant.Params.SUPPORT_CONTINUE_PAGE_STACK_KEY] = false

  // ② 从全局导航栈取"当前在哪"
  const pathStack = globalNavStack.getPathStack()
  if (pathStack.length > 0) {
    routeName = 栈顶.name
    paramStr  = JSON.stringify(栈顶.param)
  } else {
    tabIndex = getCurrentTabIndex()          // 没有压栈页面时，只记 Tab 下标
  }

  // ③ 双载体写入：普通键 + ArrayBuffer 各一份（见下）
  wantParam.routeName = routeName
  wantParam.param     = paramStr
  wantParam.tabIndex  = tabIndex
  const encoded = new util.TextEncoder().encodeInto(JSON.stringify(payload))
  wantParam.migrationData = encoded.buffer as ArrayBuffer

  return AbilityConstant.OnContinueResult.AGREE   // ④ 必须 AGREE，否则系统取消迁移
}
```

四个要点：

1. **`SUPPORT_CONTINUE_PAGE_STACK_KEY = false`**：不让系统按快照恢复整棵页面栈
   （快照里存的是组件树，跨设备/跨版本极易错位）。应用只迁移"坐标"（路由名+参数+Tab），
   落地后自己 `pushPath`——稳得多。
2. **双载体**：同一个载荷既写普通键、又写 `ArrayBuffer`。因为系统通道对
   `want.parameters` 里值的**反序列化形态不保证**（实测会拿到 ArrayBuffer 或 string），
   目的端两种都要能解（见第 4 节）。
3. **返回值必须是 `AGREE`**；返回其它值系统会取消本次迁移。
4. **隐私合规**：`migrationData` 是完整用户数据（路由+参数），**禁止 `Logger.info` 公开打日志**
   （`%{public}s` 任何人可读）。本工程全部降为 `Logger.debug`（release 下掩码）。

## 4. 目的端：解析与恢复

### 4.1 入口三分支（都在 EntryAbility）

| 场景 | 回调 | 说明 |
|---|---|---|
| 接续冷启动 | `onCreate` + **`onWindowStageRestore`** | ⚠️ 系统走 **Restore** 不走 Create，两处都要 `loadContent` |
| 接续热启动（进程还活着） | `onNewWant` | 走 `extractMigrationData` 存载荷 |
| 通知直达 | 同上 | 优先级：**通知直达 > 多端流转**（`extractNotificationRoute` 先判） |

### 4.2 解析（`extractMigrationData`）

- 优先读 `migrationData`：`ArrayBuffer → util.TextDecoder → JSON.parse`；
- 读不到再退回普通键 `routeName/param/tabIndex`（`decodeParamValue` 兼容 string/ArrayBuffer/object）；
- 解析成功 → `setMigrationPayload(...)` 存入 RouterManager 单例 + `markPendingDeepLink()`。

### 4.3 恢复（`MainTab.initAndRestoreMigration`）—— 时序是命门

```
MainTab.aboutToAppear
  └─ setTimeout(initAndRestoreMigration, COLD_START_INIT_DELAY_MS)   ← 第一级延迟
       ├─ settingsVM.init / homeVM.init / routeVM.init               ← 数据先就位
       └─ setTimeout(restoreMigrationIfNeeded, COLD_START_ROUTE_DELAY_MS)  ← 第二级延迟
            ├─ globalTabsController.changeIndex(tabIndex)            ← 切到对的 Tab
            ├─ routeName === 'MainTab' ? 结束
            └─ globalNavStack.pushPath(new NavPathInfo(routeName, param))  ← 打开同一页面
```

两级延迟的原因：**Navigation 未挂载 / NavPathStack 未绑定时 `pushPath` 会冷启动卡死**。
先 init 数据再恢复路由，是因为页面 `aboutToAppear` 里就要读 VM。

### 4.4 深链竞态协调（`pendingDeepLink`）

MainTab 冷启动原本会自动跳登录页；存在深链/流转时要**跳过它**，让迁移路由先执行，
否则会出现"登录页压在目标页上"的栈混乱。用 `markPendingDeepLink / hasPendingDeepLink /
consumePendingDeepLink` 三件套协调，恢复完成后 `notifyMigrationRestoreDone()`（一次性回调）。

## 5. 「迁回原设备」—— 你最关心的那条

**机制是对称的**：迁回 = 在目标设备上再发起一次流转。因为两台设备跑的是**同一个 App**，
目标设备的 `onContinue` 同样会打包"它当前在哪"，原设备收到后走同一套解析与恢复。
原设备应用退后台时 UI 栈原样保留（系统不杀它），所以"回到原设备的界面"在数据与窗口层面都是现成的。

### ⚠️ 本工程现状：**热启动缺口（未修，如实记录）**

`restoreMigrationIfNeeded()` 目前**只有冷启动一个调用点**（`MainTab.initAndRestoreMigration`，
由 `hasInitStarted` 保证每进程只跑一次）。而**热启动**（对端应用还活着时迁回）走的是
`onNewWant → extractMigrationData → setMigrationPayload`，**存完载荷没有任何人去消费它** ⇒
界面不会跳转，应用只是回到前台停在旧页面。

- **复现**：A 机打开目标详情 → 流转到 B 机（B 冷启动，界面正常接续 ✔）→ 在 B 机再流转回 A
  （A 的应用还活着 → 热启动）→ A 停在原来的页面，**不会**跳到 B 机当时看的页面。
- **修法（未实施，供复刻者参考）**：`onNewWant` 里 `extractMigrationData` 成功后，
  若 UI 已就绪（MainTab 已挂载）就**立即**调一次 `restoreMigrationIfNeeded()`；
  冷启动路径保持现有延迟逻辑不变。两台设备都打上这个补丁，双向迁回才完整。
- **数据一致性不是问题**：`onNewWant` 里已有 30s 节流的 `triggerSync()`，两端数据靠云同步对齐。

## 6. 移植到另一个 App 的检查清单

1. `module.json5`：ability 加 `"continuable": true`。
2. UIAbility 实现 `onContinue`：从自己的导航栈取栈顶（路由名 + 参数），打包返回 `AGREE`。
3. 决定页面栈策略：自管导航就设 `SUPPORT_CONTINUE_PAGE_STACK_KEY = false`（推荐），
   并在目的端自己 `pushPath`。
4. **双载体写入**（普通键 + ArrayBuffer），目的端两种形态都要能解。
5. `onWindowStageRestore` 与 `onWindowStageCreate` 做同样的窗口初始化。
6. 冷启动恢复**必须延迟**到 Navigation 挂载、数据 init 之后（两级 setTimeout）。
7. 有自动跳转（登录/隐私弹层/引导页）的，用 pending 标志与迁移路由协调先后。
8. 载荷只放**路由与 id**，数据由本地/云端加载——不要把业务数据塞进迁移通道。
9. 迁移载荷属用户敏感数据，日志一律脱敏（`debug` 档，禁 `%{public}s`）。
10. **补上热启动恢复**（第 5 节缺口），否则"迁回原设备"只在原应用被杀后生效。
11. 调试：`hdc shell hilog | grep -E "EntryAbility|RouterManager|MainTab"`，
    两台设备（或一台真机 + 一台模拟器）登录同一华为帐号。
