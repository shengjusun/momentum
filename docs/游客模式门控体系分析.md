# 游客模式的门控体系分析

> 分析人：阿墨　日期：2026-09-16 20:06
> 触发问题：游客模式下数据只留本地；各界面门控是否该联动一致？AI 页应"可看但锁"。

## 一、结论先说

**你的三条判断我都同意，而且主干已经是对的** —— 全工程只有 **3 处**是异类，它们用了"命令式跳转"，与整体设计不一致。

| 你的判断 | 现状 | 判定 |
|---|---|---|
| 游客模式数据只留本地 | `CloudDBSyncProxy.canSync()` 是**唯一云端闸门**；未登录 → 所有 `syncNow` early-return，HomeVM/RouteVM 不拉云，反馈走本地队列 | ✅ **已成立，无需改动** |
| 各界面门控要联动 | 主干统一（3 个机制），但 3 处用命令式跳转 | ⚠️ **需收敛** |
| AI 页可看但锁 | 已实现，且是**全工程最正确的门控范式** | ✅ 可作样板（但有 1 个待定产品语义） |

## 二、现有的三个门控机制（主干，值得保留）

1. **`CloudDBSyncProxy.canSync()`** —— 云端能力**单一闸门**（`syncEnabled && 已登录 && ...`），全 App 云操作都过它。设计得当：**用"能力"而非"身份"判定**。
2. **`AppStorage('isLoggedIn')`** —— 跨 ViewModel 解耦通道（`SettingsViewModel:1185` 登录/登出双向同步），不需要各 VM import SettingsVM。
3. **`settingsVM.userProfile.isLoggedIn`** —— `@ObservedV2` + `@Trace` 完整响应链，登录成功即自动重渲染所有读它的界面（`AIPage` 注释明确说明）。

## 三、逐能力门控矩阵（实测）

| 能力 | 游客可用？ | 门控方式 | 现状 |
|---|---|---|---|
| 四象限 / 番茄钟 / 统计 / 通知 / 桌面卡片 / 导入导出 | ✅ 可用 | 无门控 | ✅ |
| **路线页浏览 + 手动建目标** | ✅ 应当可用 | **命令式跳转** | ❌ `RoutePage:851-854` |
| **目标详情** | ✅ 应当可用（本地数据） | **命令式 replacePath** | ❌ `GoalDetailPage:1385-1389` |
| **AI 拆解 / 对话** | ⚠️ **可看，输入被锁** | 响应式引导 + `syncEnabled` 灰度 | ✅ **样板** |
| 云同步 | ❌ 不可用 | `canSync()` 闸门 + 开关点击引导登录 | ✅ |
| 反馈提交 | ✅ 可用 | `FeedbackService` 内部：未登录入**本地队列**，登录后自动补传 | ✅ |
| 资料 / 账号 | 显示"未登录"态 | 分支渲染 | ✅ |
| 桌面卡片刷新 | ✅ 可用 | 本地 | ✅ |

## 四、AI 页是样板，但里面藏着**两种不同的"锁"**

`AIPage` 里其实有两种锁法，形态不一样：

| 场景 | 表现 | 位置 |
|---|---|---|
| **未登录** | 整页替换为 `AiLoginRequiredSection`（图标 + 文案 + 去登录按钮）→ **看不到输入区** | `AIPage:1169-1172` |
| **已登录但关了云同步** | 输入区**可见但禁用**：输入框 `.enabled(false)`、发送按钮置灰、旁边一行 🔒 提示 | `AIPage:1251-1265` / `1311` / `1344-1355` |

你说"AI 界面游客**可以看**，但要锁" —— 按字面意思，**未登录时应该用第二种形态**（让游客看到 AI 界面长什么样、输入区灰着、点了引导登录），而不是整页换成引导卡。**这是一个产品选择，需要你定：**

- **方案 1**：维持现状（未登录=整页引导）→ 最干净，但游客"看不到"AI 界面本体，与你的描述有落差
- **方案 2**：未登录也渲染完整界面，只是输入区禁用 + 🔒 提示（复用已登录-but-关同步那套视觉）→ **完全符合"可看但锁"**，且复用现成组件，改动最小
- **方案 3**：两者结合（界面可见 + 顶部一条引导横幅）

## 五、真正需要收敛的：3 处命令式跳转

全工程只有这 3 处"不引导、直接跳走"，其余全部是响应式/就地处理：

| 位置 | 形态 | 问题 |
|---|---|---|
| `RoutePage:851-854` | `aboutToAppear` → `navigateTo(LOGIN)` | ① TabContent 子组件只在首次切到执行一次 → **只拦第一次**；② `navigateTo` 有 600ms 防抖会静默吞掉 |
| `RoutePage:886-889` | `onPageShow` → 同上 | `RoutePage` 非 `@Entry` → **死代码，永不执行**（项目在 `HomePage:500` 有注释承认此坑） |
| `GoalDetailPage:1385-1389` | `onDestinationReady` → `replacePath(LOGIN)` | 命令式替换栈，游客点目标卡片被踢走 |

**它们同时造成材料矛盾**：`docs/上架素材/上架文案.md:93/98` 对市场承诺"可以完全不登录…""以游客身份体验**全部本地功能**"，而 `MainTab` 的 09-11 合规改造注释、`上架差距复核报告.md:117/146`（"未登录可体验本地功能 + AI 需登录 = **唯一合规路径**"）也都指向同一口径。

## 六、建议的收敛方案（三步，按"联动"这个诉求设计）

### 第 1 步：抽一个**共享门控组件**（这才是"联动"的实体）
把 AI 专用的 `AiLoginRequiredSection` 泛化为 `common/components/LoginRequiredSection.ets`：
- 入参：图标 / 标题 / 说明 / 按钮文案 / `onNavigateLogin`
- 全 App 需要登录的地方**统一用它**，消灭各写各的

> 现状痛点：这个形态只在 `ai/AIChatComponents.ets` 里，别的页面想用只能重写一遍 → 这正是"联动不起来"的原因。

### 第 2 步：3 处命令式跳转 → 就地引导
- `RoutePage`：**直接放行**（游客本就能看路线页；空态已有引导卡 + 双入口）
- `GoalDetailPage`：改响应式 —— 未登录时页面照常渲染，仅在"需要云/AI 的动作"处给引导
- 删掉 `RoutePage.onPageShow` 那段死代码

### 第 3 步：设置页的"联动"表现
游客态下，把依赖登录的项统一加**"登录后可用"标注**（同一个样式），而不是只有一个开关自己能看出来。至少涉及：
- 云同步开关（已有引导 ✓）
- 「立即同步」按钮
- 账号资料区

## 七、顺带发现的一个**产品耦合**（需要你确认是否有意）

`AIPage` 判断"能否发消息"用的是 **`settings.syncEnabled`**，而不是登录态：

```
AIPage:495   if (!settingsVM.settings.syncEnabled) → toast ai_cloud_sync_required_toast
AIPage:1311  .enabled(!this.isLoading && settingsVM.settings.syncEnabled)
AIPage:1351  .enabled(settingsVM.settings.syncEnabled && 输入非空)
```

而 `syncEnabled` 又被"**登录即自动开启**"（`SettingsViewModel:996`）。所以实际效果是：

- 游客 → `syncEnabled=false` → AI 锁定 ✅ 符合预期
- **已登录用户手动关掉云同步 → AI 也会被一起锁掉** ⚠️

`SettingsViewModel:993` 的注释显示这是**有意为之**（"AIPage 以 syncEnabled 作为云功能门控"）。但用户视角是"我关掉同步，凭什么 AI 也不能用？"——**建议单独决策**：是保持这个耦合，还是让 AI 只认登录态（AI 走后端云函数，本身并不依赖 CloudDB 同步）。
