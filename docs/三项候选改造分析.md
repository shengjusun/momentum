## ① steps 加稳定 id（数据模型对象化）

### 关键前提：工程里已经有现成范式可照搬

| 层级 | 模型 | 步骤存储方式 |
|---|---|---|
| **L2 AI 任务** | `AiGeneratedTask` | `steps: string[]` + `completedSteps: boolean[]`（**两个平行数组**） |
| **L4 任务详情** | `TaskDetailItem` | `steps: TaskStep[]`（**已对象化**：`{ id, text, isCompleted }`） |

⇒ 这是**两代设计并存**。L4 已经用了"带 id 的对象数组"，L2 还是老的平行数组。
⇒ 改造**不是从零发明**，而是把 L2 对齐到 L4 已有的 `TaskStep` 范式（甚至可直接复用该类）。

### 要改什么（精确到位置）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `model/TaskModels.ets:52-66` `AiGeneratedTaskJSON` | `steps: string[]` + `completedSteps: boolean[]` → `steps: TaskStepJSON[]` |
| 2 | `model/TaskModels.ets:87-89` `AiGeneratedTask` | `@Trace steps: Array<string>` + `@Trace completedSteps: Array<boolean>` → `@Trace steps: TaskStep[]` |
| 3 | `model/TaskModels.ets:155-205` `fromJSON` / `toJSON` | 改序列化，并**新增老格式迁移**（见风险表） |
| 4 | `model/TaskModels.ets:358-381` `getCompletedStepsSafe` / `isStepCompleted` | 原为"按下标对齐兜底"而存在；对象化后可简化 |
| 5 | `viewmodel/RoutePageViewModel.ets`（**28 处**） | 主要读写点（勾选/增删步骤、快照） |
| 6 | `pages/TaskDetailPage.ets`（**26 处**） | 步骤列表 UI + 增删编辑 |
| 7 | `pages/GoalDetailPage.ets`（9 处） | 步骤展开区 |
| 8 | `common/services/ProfileAnalyzerService.ets`（4 处） | 完成度统计 |
| 9 | `common/utils/AiGoalFactory.ets`（3 处） | 构造任务时填 steps |
| 10 | `common/services/DeepSeekService.ets`（3 处） | **把 AI 返回的 `steps: string[]` 转成模型**（新 id 的生成点） |
| 11 | `model/Models.ets` / `RouteModels.ets` / `RoutePage.ets` / `AIChatComponents.ets`（各 1-2 处） | 导出与零散引用 |

**影响面合计：11 个文件 / 103 处引用。**

### 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **本机/云端存量数据是老格式** | `steps: string[]` + `completedSteps: boolean[]` 已落盘并已同步到 CloudDB | `fromJSON` 做**格式嗅探**：`typeof json.steps[0] === 'string'` 则判定为老格式 → 就地转换并补 id |
| **云同步跨端不一致** | `AiGeneratedTaskJSON` 是同步载荷（`RouteModel.goals[].tasks[]`）的一部分 | 未上线 ⇒ **无旧版本客户端**，风险仅限"同账号多台设备一升一未升"的测试场景 |
| **备份格式** | `ImportExportPage` 备份含 goals/tasks | 同上；⚠️ `app:'Momentum'` 是**勿动契约**，迁移只动 `steps` 字段的解析 |
| **AI 生成赋值点遗漏** | `DeepSeekService` 把 AI 的 `steps: string[]` 写进模型 | 转换点统一收口到一处函数，禁止各处自己拼 |
| **改动面大导致漏改** | 103 处引用 | 建议**单独一轮**做，不与其他改动混合；改完必须真机跑通「勾选步骤 / 增删步骤 / 冷启动恢复 / 云同步往返」四条链路 |

### 收益

1. **解锁两处 steps 列表的增删动效**（key 可去掉 `index` 与 `stepVersion`）
2. **顺带修掉一个真隐患**：现在 `completedSteps` 与 `steps` 靠**下标对齐**，任何一处漏同步就错位——`getCompletedStepsSafe` 这个函数本身就是为兜底而写的。对象化后天然对齐，不再可能出现错位。

### 时机判断（重要）

**未上线反而是最好的改造时机**：没有线上存量数据要兼容，只需处理本机/云端测试数据与迁移逻辑。
一旦上线，改造就要同时兼容新老两代数据（且旧客户端会写坏新格式），成本显著上升。

⇒ **如果你要动它，现在比以后便宜。** 但它是本轮最大的一处改动，建议**单独一轮**。

## ② AI 提示词本地化

### 现状：4 个硬编码中文提示词（`model/AppConstants.ets`）

| 常量 | 行 | 用途 |
|---|---|---|
| `DEEPSEEK_SYSTEM_PROMPT` | 12-47 | 目标拆解（含 JSON 结构说明 + 完整示例） |
| `GOAL_REVIEW_SYSTEM_PROMPT` | 50-63 | 单目标复盘 |
| `GLOBAL_REVIEW_SYSTEM_PROMPT` | 66-77 | 全局复盘 |
| `TODAY_PRIORITY_SYSTEM_PROMPT` | 80-91 | 今日待办排序建议 |

### 问题

- 英文界面下 AI **仍用中文回复**，且格式写死"分四段，每段用『一、二、三、四』开头"、"250 字以内"——这些是**中文特有的表达**，直接换语言会别扭。
- ⚠️ **关键约束**：后 3 个提示词的**输入是结构化数据**（如 `goals=3;goals_completed=1;focus_today=2`），**不含用户自然语言** ⇒ 靠"跟随用户输入语言"**无法自动解决**，必须显式告知输出语言。

### 三个方案

| 方案 | 做法 | 改动量 | 风险 |
|---|---|---|---|
| **A 最小** | 保留中文提示词，在末尾追加一行"输出语言：<lang>" | 极小 | 中文字特化的格式描述（"一、二、三、四"、字数）仍在 → 英文输出仍别扭，需同时改写格式描述 |
| **B 两套提示词** | 中/英各一套，按系统语言选择 | 中（4×2） | 后续改一处要同步另一处 |
| **C 英文主提示词 + 语言指令** | 提示词全部改写为英文，追加"respond in <lang>" | 中 | 英文提示词对中文任务的理解可能略降，需实测 |

### 建议

**推荐方案 B**：
- 提示词本质是"给模型的自然语言指令"，**用目标语言写效果最稳**（方案 C 有实测不确定性）
- 只有 4 条，维护成本可控
- 落地形态：新增 `common/constants/AiPrompts.ets`，提供按语言返回的集合；`AppConstants.ets` 里的 4 个常量迁移过去

**语言判定**：`i18n.System.getSystemLanguage()` 或 `getContext(this).config.language`

### 验证要求

改成英文后**必须真机实测 4 个场景的输出**，尤其：
- `TODAY_PRIORITY` 里"直接引用输入中的任务序号（任务1/任务2）、严禁编造任务名称"这条**隐私约束**在英文下是否仍被遵守
- `GOAL_REVIEW`/`GLOBAL_REVIEW` 的四段结构与字数限制

### 优先级

英文用户可见的质量缺陷，**但不是上架阻塞**。若应用主要面向中文用户，可降级或延后。
